## v0.2 서버 경계에서 개선한 항목

- 클라이언트 검사를 생략해도 서버가 JSON·해시·실제 바이트를 검사한다. 해시가 맞는 손상 WebP도 별도 작업자가 반려했다.
- 사용자가 owner나 승인 상태를 지정할 수 없다. 사용자 JWT 검증·초대 확인·소유권 검사와 DB RLS를 적용했다.
- 제출 원문·manifest 해시를 DB 트리거로 고정하고 Storage 덮어쓰기를 막았다. 검증은 임대 토큰과 같은 해시에 결합한다.
- 고유 제약과 트랜잭션으로 등록을 확정한다. 동시 재시도와 반복 제출에서 같은 ID를 확인했다.
- 선언 용량을 업로드 전에 예약하고 실제 스트림 크기를 제한한다. 임대 만료·재시도 상한도 DB 시험으로 확인했다.
- 작업자는 새로운 다운로드 폴더와 서버 객체를 사용한다. 사용자 MCP는 작업자 토큰·서비스 키를 받지 않는다.

## 아직 막혀 있는 제품 출시 조건

1. **공개 온보딩 부재.** 초대된 Supabase 세션으로 등록할 수 있지만 공개 OAuth 로그인·설치 UI와 기존 게임 계정 연결은 없다.
2. **AI 상대와 공정성.** 승인된 버전의 동적 목록·로딩과 공통 플레이어 규칙은 구현했다.
   등록 선수를 AI 상대로 실행하는 경로와 양쪽 경쟁 밸런스는 후속 구현이다.
3. **품질 판단.** 발 교대·접지·연타·넘어짐·얼굴 일관성은 알파·크기 검사로 증명되지 않는다.
   새로 만든 선수 하나를 실제 양쪽 전투 소비자로 재생하는 시연이 필요하다.
4. **원격 공격자 격리.** 로컬 제작 폴더는 신뢰하는 작업 폴더여야 한다.
   V8 힙 제한은 네이티브 이미지 메모리의 강제 상한이 아니며, 경로 검사도 동시 파일 교체 공격의 완전한 방어가 아니다.
   원격 작업의 불변 다운로드 디렉터리와 임대·재시도는 구현했다. OS 메모리·CPU 격리와 최대 입력 부하는 아직 검증하지 않았다.
5. **실제 Dot 사용성.** SDK 통합 시험은 통과했지만 모든 계정·호스트 UI의 도구 노출과 이미지 제작 능력을 보증하지 않는다.
   README의 첫 검사 요청으로 설치를 확인한 뒤 새로운 캐릭터 제작으로 이어간다.

6. **운영 자동화.** 작업자 PC 중단 중에는 제출이 대기한다. 자동 시작·만료 업로드 정리·자동 백업은 없다.
   예약 용량은 반려·만료 기록도 포함하므로 과잉 접수는 막지만 운영자 정리가 필요하다.

로컬 검사 성공은 등록이 아니다. 원격 결과는 DB에서 실제 생성된 선수 ID만 반환한다.
새 등록은 `runtimeApproved: false`와 남은 게임·시각 검수 단계를 표시한다.
운영자가 해시와 사용 범위를 승인한 뒤에는 실제 승인 상태와 `runtimeScope`를 조회할 수 있다.

## 게임 연결에서 개선한 항목

- 임의의 등록 패키지를 공개하지 않는다. DB가 승인 해시·사용 범위·근거를 요구하며, 공개 조회는 승인된 행만 반환한다.
- 게임은 JSON 원문과 실제 애셋의 해시를 다시 검사한다. 다운로드 출처는 설정된 Supabase 프로젝트의 전용 버킷으로 제한한다.
- 같은 서버 선수 ID는 목록에 한 번만 표시한다. 텍스처 키에는 서버 ID·manifest 해시·동작 이름이 들어간다.
- 경기 입장 때 승인을 다시 읽고 전체 동작을 준비한다. 실패하면 기존 캐릭터로 조용히 바꾸지 않고 목록에서 오류를 표시한다.
- 측면 전용 선수를 마을의 8방향 로더에 전달하면 경기 준비가 실패했다. 경기 전용 로더로 수정하고 회귀 시험을 추가했다.
- 등록 선수의 UUID가 주간 대회 저장에서 지워지던 제한을 수정했다. NPC 식별자 규칙은 유지했다.
