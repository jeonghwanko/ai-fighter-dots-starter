Reproduce in Dots

  1. Connect the reviewer

    Use the existing ODDBOUT connection and the credentials supplied only in the private review details. Call get_profile and verify the intended reviewer, then check_creation_readiness with purpose registration. Do not put credentials in chat.

  2. Recover the actual files

    Download the sample ZIP into the Dots workspace, extract fighter.json and assets/, and preserve the original bytes. Use native file inputs for the actual files. A Library page preview or a filesystem path mentioned in chat is not successful file transfer.

  3. Prepare the upload

    Call prepare_fighter_registration with the actual fighter.json and a UUID idempotency key. This immutable sample was registered with key 2e2a6bb2-fde0-42d6-9bed-473e36374794. Reusing it on the reviewer account resumes the existing result; if already registered, verify it rather than uploading or publishing again.

  4. Transfer all eleven assets

    For a new, explicitly requested test within the account limit, change the test localId/name, validate the package, and choose a fresh UUID. Upload each returned asset ID using its actual WebP file. Every response must be uploaded and its size/hash must match. Do not regenerate artwork because of a transport failure.

  5. Request final registration

    After all uploads and the authorized final-package review, call submit_fighter_registration. Poll get_fighter_submission with the returned ID until registered or rejected. Queued and validating are not completion; preserve the same submission and key while waiting.

  6. Verify ownership and result

    Call get_registered_fighter and list_my_fighters. Check the new fighter belongs to the reviewer and its immutable manifest hash matches. Deletion is a separate requested action with ownership and explicit confirmation; do not delete fixtures as an implicit cleanup step.
