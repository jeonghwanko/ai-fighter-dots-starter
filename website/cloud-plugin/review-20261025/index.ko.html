Dots에서 재현하기

  1. 심사 계정 연결

    기존 ODDBOUT 연결과 비공개 Review details에만 제공된 심사 계정을 사용합니다. get_profile로 대상 계정을 확인한 후 check_creation_readiness의 purpose를 registration으로 호출합니다. 비밀번호는 대화에 입력하지 않습니다.

  2. 실제 파일 확보

    샘플 ZIP을 Dots 작업 공간에 받아 fighter.json과 assets/를 풀고 원본 바이트를 유지합니다. 실제 파일을 네이티브 파일 입력에 전달합니다. Library 미리보기나 대화에 적힌 파일 경로만으로 전달 성공으로 판단하지 않습니다.

  3. 등록 업로드 준비

    실제 fighter.json과 UUID 재시도 키로 prepare_fighter_registration을 호출합니다. 이 불변 샘플의 키는 2e2a6bb2-fde0-42d6-9bed-473e36374794입니다. 심사 계정에서 같은 키는 기존 결과를 재개합니다. 이미 등록됐다면 다시 업로드·등록하지 않고 결과를 확인합니다.

  4. 11개 에셋 전달

    별도로 명시한 새 테스트는 계정 한도 안에서 테스트 localId·이름을 바꾸고 패키지 검증 후 새 UUID를 사용합니다. 반환된 각 에셋 ID와 실제 WebP 파일로 업로드합니다. 모든 응답이 uploaded이고 크기·해시가 일치해야 합니다. 전달 실패 때문에 그림을 다시 만들지 않습니다.

  5. 최종 등록 요청

    파일 전달과 승인된 최종 패키지 검토가 끝나면 submit_fighter_registration을 호출합니다. 같은 제출 ID로 get_fighter_submission을 조회해 registered 또는 rejected까지 확인합니다. queued·validating은 완료가 아니며 대기 중에는 제출물과 키를 유지합니다.

  6. 소유권과 결과 확인

    get_registered_fighter와 list_my_fighters로 심사 계정의 새 캐릭터인지, 불변 매니페스트 해시가 일치하는지 확인합니다. 삭제는 소유권·명시적 확인이 필요한 별도 요청이며 테스트 정리를 이유로 임의 삭제하지 않습니다.

공개 디렉터리의 기존 1.0.3 심사는 유지합니다. 이 보충 자료는 제출 ZIP 교체·심사 취소·공개 완료를 뜻하지 않습니다. 실행에는 Supabase 클라우드 주소를 사용하는 기존 개발 연결을 사용했고, 공개 게이트웨이 검증은 이전 심사 자료에 별도로 기록돼 있습니다.
